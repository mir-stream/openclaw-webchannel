## P0-1. Gateway direct WebSocket 완전 삭제

### 결정과 이유

Gateway가 browser용 WebSocket endpoint를 여는 것은 이 프로젝트의 zero-inbound 전제와
정면으로 충돌한다. 실제 사용자가 없으므로 deprecated 상태로 유지하지 않고 코드와 공개
API에서 삭제한다. NATS가 WebSocket transport를 사용할 수 있다는 사실과 Gateway direct
WebSocket은 별개다. `ws` dependency는 NATS client가 계속 사용할 수 있다.

### 현재 코드 지도

- Plugin entry: `packages/plugin/index.ts`
- Gateway WS transport: `packages/plugin/src/transport.ts`
- Transport tests: `packages/plugin/src/transport.test.ts`
- Browser legacy client: `packages/client/src/client.ts`
- Client tests: `packages/client/src/client.test.ts`
- Public exports: `packages/client/src/index.ts`
- Legacy wire/options: `packages/client/src/types.ts`
- Smoke drivers: `smoke/`
- 현재형 설명: root `README.md`, `packages/client/README.md`, `docs/STATUS.md`,
  `docs/AUTH.md`, `docs/BACKLOG.md`, `docs/PACKAGING.md`, `docs/PLAN.md`

### 코드 탐색 키

```bash
rg -n 'WebChannelClient|WebChannelTransport|handleUpgrade|registerFull|\?ticket=|Gateway-WS' \
  packages smoke docs README.md
rg -n 'sendTextToAnyOpen|soleOpenSocket|safeSend' packages/plugin
```

주요 symbol:

- `WebChannelClient`
- `WebChannelTransport`
- `handleUpgrade`
- `safeSend`
- `sendTextToAnyOpen`
- `sendApprovalRequest`, `sendApprovalResolved`

### 숨은 의존관계

`channel.ts`, `inbound.ts`, `approvals.ts`, `message-adapter.ts`가 legacy class인
`WebChannelTransport`를 타입으로 참조한다. 파일부터 삭제하면 production NATS path도 깨진다.
먼저 NATS path가 실제 사용하는 최소 interface를 shared production module로 옮긴다.

새 interface에 다음 legacy 의미를 보존하지 않는다.

- 아무 socket이나 고르는 fallback
- sole-open-socket 추측
- Gateway WS backpressure 정책
- `?ticket=` upgrade carrier

### 구현 작업

1. Shared interface 추출 후 NATS channel과 approval/inbound adapter가 이를 사용하도록 변경
2. Plugin `index.ts`, WS transport 및 테스트 삭제
3. `WebChannelClient`, 전용 option/wire type 및 테스트 삭제
4. Package root export 제거
5. Gateway-WS smoke script 삭제
6. 현재 문서에서 사용법 제거; 역사 문서는 archive 표기
7. Package tarball과 OpenClaw extension manifest가 NATS entry만 포함하는지 확인

### 호환성

`WebChannelClient`는 공개 root export이므로 형식상 breaking change다. 실제 소비자가 없다는
결정에 따라 명시적인 breaking 0.x release로 처리한다. `auth.ts` 전체를 삭제하면 안 된다.
NATS registration의 JWT 검증에서도 사용되므로 Gateway upgrade 전용 caller/comment만 제거한다.

### 필요한 테스트

- Package export에 `WebChannelClient`가 없음을 검증
- Packed plugin에 `index.ts`/Gateway route가 없음을 검증
- OpenClaw gateway boot 후 browser-facing inbound listener가 생기지 않음을 검증
- 기존 NATS live harness 전체 통과
- `rg` 기반 금지 symbol CI check 고려

### 완료 조건

- `WebChannelClient`, `WebChannelTransport`, `?ticket=` production symbol 0개
- Gateway가 browser용 socket/upgrade route를 등록하지 않음
- NATS build, pack-load smoke, examples, live harness 통과
- 현재형 문서가 Gateway-WS를 지원 surface로 언급하지 않음

## P0-2. Auto-admission과 unauthenticated handshake 완전 삭제

### 실제 문제

Auto-admission은 NATS subject에 접근할 수 있다는 이유만으로 application peer를 허용한다.
이 경로의 per-connection X25519 key exchange는 상대 key의 신원을 검증하지 않는다. NATS
relay가 active attacker이면 browser와 agent 사이에서 각자 다른 key exchange를 수행해
plaintext를 중간에서 읽고 다시 암호화할 수 있다.

이는 dev risk로 수용하지 않는다. 관련 fallback을 남기면 새 기능이 실수로 이 경로를 다시
사용할 수 있으므로 설정부터 wire frame까지 삭제한다.

### 현재 코드 지도

- Credential/admission 결정: `packages/plugin/src/nats-credential-source.ts`,
  `packages/plugin/src/nats-admission.ts`, `packages/plugin/src/account-config.ts`
- Plugin handshake/session: `packages/plugin/src/nats-channel.ts`,
  `packages/plugin/src/e2e-session.ts`, `packages/plugin/src/e2e-crypto.ts`
- Client fallback: `packages/client/src/nats-client.ts`,
  `packages/client/src/e2e-crypto-browser.ts`
- Plugin composition: `packages/plugin/index-nats.ts`
- Config schema: `packages/plugin/openclaw.plugin.json`
- 관련 문서: `docs/STATUS.md`, `docs/BACKLOG.md`, package README, onboarding 문서
- Demo/e2e flags: `demo/`, `e2e/`, `.ouroboros/`

### 코드 탐색 키

```bash
rg -n 'admission.*auto|DEV_OPEN|devOpen|key_exchange|handleHandshake|deriveConversationKey' \
  packages demo e2e docs
rg -n 'peerSessionKeys|handshake|wildcard.*peer|subscribeWildcard' packages/plugin/src
rg -n 'wrappedConversationKey|pinnedAgent|registerWithPop' packages/client/src
```

주요 symbol/문자열:

- `WEBCHANNEL_NATS_DEV_OPEN`
- `admission: "auto"`
- `handleHandshake`
- `key_exchange`
- `peerSessionKeys`
- `deriveConversationKey`
- `wrappedConversationKey`
- `registerWithPop`

### 삭제할 동작

- Open NATS connection을 인증 대신 사용하는 credential fallback
- Register하지 않은 peer의 wildcard `.in` 구독
- Client/agent의 live `key_exchange` frame
- Client 설정에 device X25519 key가 없을 때 사전 선택되는 legacy handshake 경로
  (`nats-client.ts`의 `registerDeliveredKey` 분기. 참고: register response의 wrapped key
  누락은 이미 fail-closed terminal이며 handshake로 내려가는 fallback은 존재하지 않는다)
- Auto peer용 session-key cache와 snapshot/history 전달
- Dev-open 환경변수, schema, setup prompt, test fixture

### 남겨야 할 암호 기능

- SaaS-attested browser device key
- SaaS-attested agent identity key 또는 agent key set
- Register response에서 device key로 감싼 conversation key
- Routing metadata를 AAD에 묶는 ChaCha20-Poly1305 envelope
- Replay/idempotency protection

### Migration 동작

구 config에서 auto/dev-open 설정을 발견하면 조용히 무시하지 말고 migration error를 낸다.
오류에는 제거된 설정명, 필요한 authenticated enrollment 항목, 재설정 명령을 포함한다.

### 필요한 공격 테스트

- Relay가 browser device key를 치환하면 plugin registration 실패
- Relay가 agent key/wrapped conversation key를 치환하면 browser 실패
- Register하지 않은 valid NATS user가 `.in`에 publish해도 agent turn이 시작되지 않음
- Bootstrap JWT의 peer/account/tenant/device binding 치환 실패
- Wrapped key가 없는 register response는 terminal failure이며 fallback 없음

### 완료 조건

- `auto`, `DEV_OPEN`, unauthenticated `key_exchange` runtime caller 0개
- 모든 peer가 authenticated registration 이후에만 active subscription을 가짐
- BYO-NATS와 managed NATS가 동일 protocol/invariant 사용
- 양방향 key-substitution integration test 통과

## P0-3. BYO-NATS authenticated registration 단일화

### 제품 계약

BYO-NATS는 relay 선택권이지 인증 생략 옵션이 아니다. Self-hosted, Synadia, 기타 managed
NATS 모두 동일한 application identity와 key attestation을 사용한다.

### 현재 코드 지도와 탐색 키

- Registration producer: `packages/client/src/pop-register.ts`,
  `packages/client/src/nats-client.ts`
- Registration consumer: `packages/plugin/src/nats-register.ts`,
  `packages/plugin/src/register-pop-gate.ts`, `packages/plugin/src/nats-channel.ts`
- JWT verification: `packages/plugin/src/jwt.ts`, `packages/plugin/src/jwks.ts`
- Credential mint: `packages/saas/src/nats-user-creds.ts`
- Bootstrap claims: `packages/saas/src/bootstrap-claims.ts`
- Enrollment result: `packages/saas/src/device-flow-enrollment.ts`

```bash
rg -n 'registerWithPop|handleRegister|register-pop|cnf|wrappedConversationKey|agentPublicKey' packages
rg -n 'issuerAccountId|permissions|allow.*publish|allow.*subscribe' packages/saas packages/plugin
```

### 구현 시 검증할 binding

- JWT signature, issuer, audience, expiry
- `tenant`, `accountId`, `peerId`
- Browser device public key와 PoP signature
- Target `agentId` 및 attested agent key/key set
- Register request subject의 peer와 verified claim의 peer 일치
- Reply subject가 요청자 자신의 `reginbox`인지 확인
- NATS credential subject permission이 위 identity와 일치

### BYO 운영 계약

Library/setup은 필요한 permission template과 preflight 검증을 제공한다. BYO operator가 더
넓은 permission을 설정한 경우 최소한 명확히 진단하며, application identity 검증은 broker
permission이 올바르다는 가정만으로 생략하지 않는다.

### 완료 조건

- Self-hosted와 external account live harness가 같은 registration suite를 공유
- 잘못된 issuer/audience/account/peer/device/agent binding이 모두 fail-closed
- Register 이전 ciphertext/message publish가 turn을 생성하지 않음
- Active relay가 register reply를 redirect하거나 key를 바꿔치기할 수 없음

## P0-4. 전송 결과 계약과 false-success 제거

### 실제 실패 시나리오

Plugin outbound adapter는 targeted send와 fallback의 boolean 결과를 무시하고 synthetic
message ID를 반환할 수 있다. NATS reconnect 중 `sendToPeer()`가 `false`를 반환해도 core는
성공으로 본다. Client는 unacked cap을 넘기거나 explicit close/credential rotation을 수행할
때 pending message를 호출자에게 실패로 알리지 않고 제거할 수 있다.

### 현재 코드 지도

- Plugin outbound facade: `packages/plugin/src/channel.ts`
- Lazy/primary transport binding: `packages/plugin/index-nats.ts`
- NATS peer send: `packages/plugin/src/nats-channel.ts`
- Client queue/unacked ledger: `packages/client/src/nats-client.ts`
- Public wrapper state: `packages/client/src/nats-client-wrapper.ts`
- Ingress ACK semantics: `packages/plugin/src/ingress-dedupe.ts`
- Public message status type: `packages/client/src/types.ts`

### 코드 탐색 키

```bash
rg -n 'sendTextToAnyOpen|sendToPeer|return.*messageId|boundChannel|lazyTransport' packages/plugin
rg -n 'unackedLedger|MAX_UNACKED|flushQueue|retryUnacked|clear\(\)' packages/client/src
rg -n 'delivered|accepted|sendAck|message_ack|ack' packages/client/src packages/plugin/src
```

관찰할 snippet 형태:

```ts
transport.sendText(...)
transport.sendTextToAnyOpen(...)
return { messageId: ... }
```

위처럼 send 결과와 무관하게 success result를 만드는 caller를 전부 제거해야 한다.

### 목표 상태 모델

```text
queued -> sent -> accepted -> completed
            \-> failed(reason)
```

- `queued`: 로컬에 보관됐지만 socket에 쓰지 못함
- `sent`: NATS publish 요청을 기록함. 아직 plugin 수락을 의미하지 않음
- `accepted`: Plugin ingress가 검증·dedupe 후 turn 처리 대상으로 수락함
- `completed`: Turn이 정상적으로 settle됨
- `failed`: 더 이상 자동 진행하지 않으며 원인과 retry 가능 여부가 있음

### Public API 권고

- `send()`는 stable `messageId`와 receipt/state handle을 반환
- 상태에는 `reason`, `retryable`, `lastAttemptAt` 포함
- Broker publish 불가 시 동기 throw 또는 receipt의 즉시 `failed`
- Reconnect retry는 동일 ID를 유지해 plugin dedupe와 결합
- Terminal auth, queue overflow, explicit cancellation은 모든 pending receipt를 `failed`
- `delivered` 명칭은 의미가 과하므로 `accepted`로 변경
- Turn completion과 ingress acceptance를 별도 event로 유지

### 내구성 경계

이 항목이 반드시 disk-backed durable queue를 요구하는 것은 아니다. Process/browser 종료로
pending state가 사라질 수 있다면 그 보장 범위를 API와 UI에 명시한다. 살아 있는 process가
실패를 알고도 성공을 반환하거나 console warning만 남기고 버리는 것은 금지한다.

### 필요한 테스트

- Send 시 socket disconnected
- Publish 직전/직후 NATS disconnect
- ACK 전 reconnect와 duplicate retry
- Unacked cap 도달
- Explicit close, logout, credential rotation
- Terminal authorization error
- Plugin targeted send 실패 + fallback 실패
- ACK는 왔지만 turn이 실패/취소됨

각 테스트는 최종적으로 `accepted`, `completed`, `failed` 중 하나를 관찰해야 한다.

### 완료 조건

- `false` send 결과를 무시하고 success ID를 반환하는 caller 0개
- Queue/ledger에서 console-only eviction 0개
- 모든 pending message가 관찰 가능한 terminal 또는 accepted state로 귀결
- UI가 `sent`와 `accepted`를 혼동하지 않음
