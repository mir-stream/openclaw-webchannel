## P1-1. Multi-agent identity, key registry, routing

### 실제 문제

현재 registry는 `(tenant, accountId)`에 agent public key 하나만 저장한다. 같은 account에
두 번째 agent가 등록되면 첫 번째 key를 덮어쓴다. Account 미지정 값도 문자열 `default`와
같은 key로 normalize되어 실제 account와 충돌한다. 현재 NATS subject와 bootstrap 선택에도
target `agentId`가 없어 서로 다른 논리 agent를 구분할 수 없다.

### 현재 코드 지도

- Registry interface/Memory implementation: `packages/saas/src/agent-key-registry.ts`
- Enrollment approval 시 registry write: `packages/saas/src/device-flow-enrollment.ts`
- Reference bootstrap key lookup: `packages/saas/reference/enrollment-server.ts`
- Example bootstrap key lookup: `examples/webchannel-app/server/index.ts`
- NATS subject construction/parsing: `packages/plugin/src/nats-channel.ts`,
  `packages/plugin/src/subject-token.ts`, `packages/client/src/nats-client.ts`
- Bootstrap claims/result types: `packages/saas/src/bootstrap-claims.ts`,
  `packages/saas/src/device-flow-types.ts`

### 코드 탐색 키

```bash
rg -n 'AgentKeyRegistry|MemoryAgentKeyRegistry|agentKeyRegistryKey|DEFAULT_REGISTRY_ACCOUNT_ID' packages examples
rg -n 'agentPublicKey|pinnedAgent|webchannel\.\$\{|subjectPrefix|peerId' packages
```

주요 symbol:

- `AgentKeyRegistry.put`, `AgentKeyRegistry.get`
- `agentKeyRegistryKey`
- `DEFAULT_REGISTRY_ACCOUNT_ID`
- `agentPublicKey`
- `pinnedAgentPublicKey`

### 먼저 결정할 의미

동일 account의 여러 process가 다음 중 무엇인지 wire에서 구분해야 한다.

1. 서로 다른 logical agent: 각자 `agentId`, session, routing target을 가짐
2. 하나의 logical agent의 HA replica: shared identity/state 또는 허용된 active key set을 가짐

두 모델을 같은 last-write-wins key로 처리하면 안 된다.

### 권장 데이터 모델

```ts
type AgentIdentityRecord = {
  tenant: string;
  accountId: string;
  agentId: string;
  keyId: string;
  publicKey: string;
  status: "active" | "rotating" | "revoked";
  enrolledAt: number;
  revokedAt?: number;
};
```

필요 API:

- `getAgent(tenant, accountId, agentId)`
- `listAgents(tenant, accountId)`
- version/CAS가 있는 `replaceKey`
- `revokeAgent`, `revokeKey`
- key rotation overlap 조회

### Cross-package 변경

- Enrollment 결과에 stable `agentId`
- Browser bootstrap에서 접근 가능한 target agent 선택
- 서로 다른 logical agent라면 JWT claims와 NATS subject에 `agentId`
- Plugin account runtime map도 account만이 아니라 agent identity를 보존
- Browser가 단일 key 또는 SaaS-signed active key set을 검증
- History/conversation key namespace도 agent identity와 충돌하지 않게 변경

### 필요한 테스트

- 같은 tenant/account에 agent A/B 등록 후 두 key 모두 조회
- A 선택 browser가 B subject/key로 redirect될 때 실패
- Literal account `default`와 missing account가 충돌하지 않음
- Key rotation overlap 중 old/new agent 모두 허용, revoke 후 old key 거부
- HA replica와 distinct logical agent fixture를 분리

### 완료 조건

- Agent key last-write-wins overwrite 경로 없음
- 모든 bootstrap/session/subject가 target agent identity를 명확히 보존
- Multi-agent E2E isolation test 통과

## P1-2. Atomic enrollment repository SPI

### 실제 문제

현재 `EnrollmentStore`는 `save/get/update/delete` 형태의 unconditional CRUD다. Library가
`get pending -> credential mint -> update approved`를 수행하고 process-local Map lock으로만
경합을 막는다. 두 issuer replica가 같은 store를 사용하면 둘 다 pending을 읽어 서로 다른
credential을 만들 수 있다. Approve와 deny도 서로의 terminal state를 덮어쓸 수 있다.

또한 approved enrollment를 먼저 저장한 다음 agent registry에 key를 쓴다. Registry write가
실패하면 live credential은 남지만 agent attestation이 없다. Retry는 already-approved fast
path로 들어가 registry를 복구하지 않는다. 하류 방어가 하나 있어 — bootstrap의 registry
`get`이 null을 반환하면 browser가 register-hop pin에서 fail-closed되므로 — 불안전 연결로
이어지지는 않지만, 복구 불가능한 partial state 자체는 실재한다.

### 현재 코드 지도

- Store SPI와 memory store: `packages/saas/src/device-flow-enrollment.ts`
- Enrollment states: `packages/saas/src/device-flow-types.ts`
- Process-local lock: 같은 파일의 `userCodeLocks`, `withUserCodeLock`
- Approval: `approve`, `approveInner` 계열
- Denial: `deny`, `denyInner` 계열
- Registry write: approval 후 `agentKeyRegistry.put` 호출부

### 코드 탐색 키

```bash
rg -n 'interface EnrollmentStore|MemoryEnrollmentStore|updateEnrollment|userCodeLocks|withUserCodeLock' packages/saas/src
rg -n 'status:.*approved|status:.*denied|agentKeyRegistry\.put|already.*approved' packages/saas/src
```

### Library와 integrator 책임

Library 책임:

- Atomic domain transition contract
- Version, operation ID, lease와 idempotency 의미
- Approval result와 agent identity record를 하나의 commit으로 표현
- Store conformance suite
- Crash/retry 상태 machine

Integrator 책임:

- PostgreSQL/Redis/SQLite 등의 실제 transaction/CAS
- Secret encryption/KMS
- Replication, backup, migration, monitoring
- Admin session과 edge rate limiting

### 권장 상태 machine

```text
pending --claim(opId, lease)--> approving --commit--> approved
   |                              |
   +----------deny--------------> denied
                                  |
                                  +--lease expired--> recover/retry
```

권장 SPI의 의미 예:

- `createPending`: device code와 user code unique insert
- `claimApproval`: expected pending/version CAS, operation ID와 lease 기록
- `commitApproval`: operation ID가 소유한 claim에 result + agent record atomic commit
- `tryDeny`: pending 상태에만 terminal deny
- `getOperationResult`: retry가 winning persisted result를 회수
- `recordPoll`: last poll과 slowdown state atomic update

Credential mint를 DB transaction callback 내부에서 수행하지 않는다. 비동기/CPU 작업 중
transaction을 오래 잡지 않도록 claim lease 후 mint, 짧은 commit으로 나눈다.

### 필요한 conformance 테스트

- 두 `DeviceFlowEnrollment` instance의 concurrent approve
- Approve vs deny race
- Claim 후 process crash와 lease recovery
- Mint 성공 후 commit timeout/retry
- Registry commit failure가 별도 partial state를 만들지 않음
- Idempotent retry가 동일 credential/result 반환
- Unique device/user code collision

### 완료 조건

- Public SPI만 구현해 multi-replica-safe issuer 구성 가능
- Process-local lock은 최적화일 수 있으나 correctness 전제는 아님
- Approved credential과 agent identity가 항상 함께 commit됨

## P1-3. NATS transport correctness와 liveness

### A. Reconnect 후 unsubscribe SID 불일치

`NatsChannel`은 subscribe 당시 numeric SID를 저장한다. Transport reconnect는 subscription을
새 SID로 replay하지만 channel의 기존 handle을 갱신하지 않는다. 이후 unregister/eviction이
old SID에 UNSUB를 보내 live subscription이 남는다.

코드 지도:

- `packages/plugin/src/nats-channel.ts`: peer subscription map, `registerPeer`, `unregisterPeer`
- `packages/plugin/src/nats-transport.ts`: `subscribe`, `unsubscribe`, reconnect replay

탐색:

```bash
rg -n 'subscriptions|peerSubscriptions|subscribe\(|unsubscribe\(|nextSid|replay' packages/plugin/src
```

수정: wire SID가 아닌 stable logical subscription handle을 caller에 반환하고 transport가
current SID mapping을 소유한다.

테스트: `subscribe -> reconnect -> unsubscribe(original handle)` 후 새 socket에 replay된 SID의
UNSUB가 기록되고 internal handler map이 비어야 한다.

### B. NATS byte length를 JS 문자 길이로 처리

NATS `MSG` length는 UTF-8 byte count다. Client와 plugin은 incoming bytes를 string으로
decode한 뒤 `string.length/slice`로 payload를 자른다. 한글/emoji/binary와 multibyte split에서
frame boundary가 깨진다.

코드 지도:

- `packages/client/src/nats-client.ts`: WebSocket `onmessage`, receive buffer, `drainBuffer`
- `packages/plugin/src/nats-transport.ts`: WS `message`, `processBuffer`/MSG parsing

탐색:

```bash
rg -n 'TextDecoder|toString\("utf8"\)|drainBuffer|MSG |byteCount|payloadLength' packages/client/src packages/plugin/src
```

수정: Buffer/Uint8Array accumulator, byte 단위 CRLF/header 탐색, exact payload length 검증.
Control line, single payload, total buffer의 최대 크기를 각각 둔다.

테스트: 한글, emoji, binary, multibyte split, 한 frame에 MSG 2개, huge/incomplete length,
missing CRLF.

### C. Connect/INFO/PONG timeout 없음

WebSocket을 열고 INFO/PONG을 보내지 않는 peer가 초기 startup 또는 reconnect를 무기한
멈출 수 있다.

탐색:

```bash
rg -n 'connect\(\)|handshakeDone|INFO|PONG|scheduleReconnect|reconnectAttempts' packages/plugin/src/nats-transport.ts
```

수정: TCP/WS open, INFO, auth CONNECT, initial PONG 단계별 deadline. Timeout은 socket을 닫고
현재 attempt를 reject한 뒤 backoff로 넘긴다.

### D. Async continuation이 새 connection을 오염 — 대부분 방어됨, 잔여 2건

register와 conversation-key unwrap 경로의 `connectionEpoch` guard는 **이미 구현되어 있다**.
`onConnected`가 epoch를 capture하고 register 성공/실패, key unwrap, legacy keygen 뒤에서
각각 재검사한다. Reconnect가 old continuation에 덮어써지는 시나리오는 방어된 상태다.

남은 잔여 이슈는 두 가지다.

1. 명시적 `disconnect()`가 epoch를 증가시키지 않는다. 현재는 `connected=false`라 publish가
   no-op이 되어 실제 피해는 없지만, 방어를 epoch 규약으로 일원화하려면 disconnect 시작 시 즉시
   증가시킨다.
2. Legacy handshake derivation(`handleRaw`)은 pre-await guard만 있고 post-await 검사가 없다.
   이 경로 자체가 P0-2 삭제 대상이므로 삭제로 해소된다.

탐색:

```bash
rg -n 'connectionEpoch|sessionKey =|unwrapConversationKey|registerWithPop|flushQueue' packages/client/src/nats-client.ts
```

### 완료 조건

- Reconnect subscription leak 0
- Parser가 byte-correct하고 memory-bounded
- Silent peer가 startup/reconnect를 무기한 막지 못함
- Old async continuation이 새 connection state를 변경하지 못함

## P1-4. Production-grade reference/demo/example

### 평가 원칙

Zero-setup development mode는 허용하지만 production 참고자료가 insecure pattern을 정상
구현처럼 보여주면 안 된다. Production profile은 security dependency가 없으면 fail-closed하고,
공격 실험용 harness는 별도 명칭과 경로로 격리한다.

### Reference enrollment server

경로: `packages/saas/reference/enrollment-server.ts`,
`packages/saas/reference/enrollment-ui.html`

검색 키:

```bash
rg -n 'Access-Control-Allow-Origin|approve|deny|createServer|Set-Cookie|USER_CODE|user_code|body \+=|data \+=' packages/saas/reference
```

확인된 문제:

- 인증 없는 approve/deny 및 administration
- Wildcard CORS와 state-changing endpoint
- CSRF 방어 없음
- Body size 제한 없는 accumulator (`body +=`)
- `Secure` attribute 없는 cookie (HttpOnly와 SameSite=Lax는 설정되어 있음)
- In-memory session/store/registry
- Query `user_code`의 reflected XSS: 서버측 `{{USER_CODE}}` 무이스케이프 치환이 HTML과
  JS string literal 양쪽에 삽입됨 (`renderApprovalPage`의 `replaceAll`; UI의 `innerHTML`은
  별개 필드용이므로 sink는 template 치환 쪽이다)

### Reference bootstrap server

경로: `packages/saas/reference/bootstrap-server.ts`

검색 키:

```bash
rg -n 'bootstrap|peerId|tenant|accountId|Access-Control-Allow-Origin|createServer|generate' packages/saas/reference/bootstrap-server.ts
```

호출자가 tenant/account/peer를 선택할 수 있는 unauthenticated signing oracle, ephemeral trust
chain, unbounded body, permissive validation을 제거한다. Production reference에서는 authenticated
session의 identity와 server-side authorization으로 claims를 만들게 한다.

### Example app

경로: `examples/webchannel-app/server/`, `examples/webchannel-app/web/`

검색 키:

```bash
rg -n 'tmpdir|MemoryAgentKeyRegistry|MemoryEnrollmentStore|sessions =|ADMIN_TOKEN|console\.log|rate.limit' examples/webchannel-app
```

확인할 항목:

- PID 기반 temp trust root
- Memory registry/store/session
- 자동 생성 admin bearer token 로그 출력
- HTTP default와 proxy/TLS 계약 부재
- Rate limit TODO

### Demo UI

`demo/web/src/app.ts`의 logout은 local teardown/reload만 수행하고 server session을 지우지 않는다.
`demo/saas-server.ts`에 logout route를 추가해 SID 삭제와 expired cookie를 처리한다.

탐색:

```bash
rg -n 'logout|tryResumeSession|location\.reload|sessions|Set-Cookie|/me' demo
```

### 구현 목표

- `NODE_ENV=development` 또는 명시적 flag에서만 zero-setup 허용
- Production mode는 durable store, external secret, session/auth 설정 없으면 부팅 실패
- Body/schema/time/rate limits
- Secure/HttpOnly/SameSite cookie와 reverse-proxy/TLS contract
- Restrictive CORS, CSRF, CSP, output encoding
- Durable CAS adapter 예제 또는 명확한 adapter skeleton과 conformance test
- 공격 harness는 `test-harness`로 분리하고 deploy 금지 guard

### 필요한 보안 테스트

- Unauthenticated approve/deny/bootstrap 거부
- 다른 user/account의 bootstrap 거부
- CSRF와 hostile Origin 거부
- Oversized JSON 조기 종료
- Crafted `user_code`가 script/HTML로 실행되지 않음
- Production profile이 memory store/temp trust root로 부팅하지 않음
- Logout 후 `/me` unauthorized

### 완료 조건

- Production reference에 signing oracle과 unauthenticated admin endpoint가 없음
- Development-only mode가 production에서 fail-closed
- README가 development와 production topology를 명확히 분리
