## P3-1. Demo session과 async UI lifecycle

### Logout이 실제 logout이 아님

Demo logout handler는 widget teardown 후 reload하지만 server-side SID를 삭제하지 않는다.
Reload 후 `/me`를 호출해 같은 session을 복원하므로 user 전환과 공용 단말 logout이 실패한다.

코드 지도:

- UI session resume/logout: `demo/web/src/app.ts`
- Session Map, cookie, `/me`, `/login`: `demo/saas-server.ts`

탐색:

```bash
rg -n 'tryResumeSession|logout|location\.reload|/me|/login|sessions|Set-Cookie' demo
```

수정:

- `POST /logout`에서 SID 삭제
- SameSite/Secure/HttpOnly 속성을 유지한 expired cookie 반환
- UI는 logout 응답을 기다린 뒤 local credential/widget state 폐기
- Logout 실패를 reload로 숨기지 않음

테스트: login → `/me` 성공 → logout → `/me` 401, reload 후 login 화면.

### Account tab widget mount race

빠른 tab 전환 시 여러 `mountLane()`이 동시에 실행되어 늦게 끝난 stale widget이 DOM과
`laneTeardown`을 덮어쓸 수 있다. 이전 NATS client가 추적되지 않은 채 살아남을 수 있다.

탐색:

```bash
rg -n 'mountLane|laneTeardown|createWidget|selectedAccount' demo/web/src/app.ts
```

수정: monotonically increasing generation 또는 AbortController. 각 await 후 generation을
검사하고 stale result는 즉시 dispose한다.

## P3-2. Subscriber exception isolation

### 문제

Public reducer/wrapper가 subscriber를 직접 순회한다. Listener 하나가 throw하면 뒤 listener가
snapshot을 받지 못하고 async message callback에서 unhandled failure가 발생할 수 있다.

코드 지도:

- Legacy client reducer는 P0 삭제 대상: `packages/client/src/client.ts`
- Production wrapper: `packages/client/src/nats-client-wrapper.ts`
- Lower NATS listener dispatch: `packages/client/src/nats-client.ts`

탐색:

```bash
rg -n 'listeners|subscribers|for \(const.*listener|emit\(|listener\(' packages/client/src
```

수정: listener별 try/catch, 나머지 listener 계속 호출, host가 제공한 error reporter로 예외
전달. Subscriber 예외가 transport state transition을 rollback하지 않게 한다.

테스트: 첫 listener throw, 둘째 listener는 정확히 한 번 호출, unhandled rejection 없음.

## P3-3. Persisted trust-root validation

### 문제

새 파일 생성 시 mode를 제한하지만 기존 trust file을 읽을 때 symlink, owner/mode, secret/public
material의 cryptographic coherence를 충분히 검증하지 않는다. Concurrent first boot도 명확히
해결되지 않았다.

코드 지도:

- `packages/saas/src/persistent-trust-chain.ts`
- `packages/saas/src/setup-trust-chain.ts`
- 관련 tests: `persistent-trust-chain.test.ts`, `setup-trust-chain.test.ts`

탐색:

```bash
rg -n 'loadOrCreateTrustChain|readFile|writeFile|chmod|mode|rename|lstat|privateKey|jwks' packages/saas/src
```

수정 체크리스트:

- `lstat/fstat`, regular-file, owner와 restrictive mode 검증
- Symlink/no-follow 정책
- Exclusive create 또는 file lock으로 first boot race 처리
- RSA private key ↔ JWKS public key/kid 검증
- NKEY seed ↔ account public key/JWT/resolver 검증
- Persisted mode와 요청된 self-contained/external mode 불일치 거부
- Corrupt/insecure file을 조용히 덮어쓰지 않고 actionable error

테스트: 0644 file, symlink, mismatched PEM/JWK, wrong NKEY seed, concurrent create, mode mismatch.

## P3-4. Bootstrap claim input validation

### 문제

Base64url을 decode한 길이만 확인하면 Node decoder가 invalid character를 무시할 수 있다.
`ttlSeconds`, `nowSeconds`, issuer/audience/peer identifiers도 NaN, Infinity, negative 또는
비정규 값을 허용할 여지가 있다.

코드 지도:

- `packages/saas/src/bootstrap-claims.ts`
- `packages/saas/src/bootstrap-issuer.ts`
- `packages/plugin/src/jwt.ts`

탐색:

```bash
rg -n 'buildBootstrapClaims|base64url|ttlSeconds|nowSeconds|audience|peerId|cnf' packages/saas/src packages/plugin/src
```

수정:

- 32-byte key의 canonical base64url 길이/문자 regex와 round-trip 검증
- Timestamp는 finite safe integer
- TTL은 positive, bounded integer
- Issuer URL/canonical identifier 정책
- Tenant/account/peer/audience에 subject-token 및 empty-string validation

테스트: invalid char가 섞인 43자 key, padded/noncanonical encoding, NaN/Infinity, negative TTL,
empty audience element, wildcard/dotted subject identifier.

## P3-5. Dead crypto와 misleading code 제거

`packages/saas/src/setup-trust-chain.ts`에 실제 public path가 사용하지 않는 simplified/placeholder
NKEY generation 또는 signing helper가 남아 있다면 제거한다. 보안 코드에서 “unused지만 그럴듯한
구현”은 미래 caller가 잘못 재사용할 가능성을 만든다.

탐색:

```bash
rg -n 'simplified|placeholder|fake|TODO.*crypto|signing|generate.*Nkey' packages/saas/src/setup-trust-chain.ts packages/saas/README.md
```

완료 조건: Production crypto primitive는 공식 library 기반 caller만 남고 README 설명과 일치.

## P3-6. 문서, version, CI 검증 정합성

### 확인된 drift

- Package manifests는 0.2.0인데 일부 문서는 0.1.x publish 상태를 현재형으로 설명
- README test count와 실제 suite가 크게 다름
- CI test floor가 현재 규모보다 매우 낮아 대규모 test 삭제를 잡지 못할 수 있음
- Historical Gateway-WS/auto-admission 문서가 현재 지원 surface처럼 검색됨

### 코드/문서 탐색 키

```bash
rg -n '0\.1\.|731 tests|712|Gateway-WS|auto-admission|dev-only' README.md docs packages/*/README.md .github
rg -n 'BASELINE|numPassedTests|vitest' .github/workflows vitest.config.ts
```

### 수정 방향

- `STATUS.md`를 실제 current-state truth로 갱신
- 제거 완료 후 Gateway-WS/auto-admission 현재형 문구 삭제
- 역사 설계는 `docs/archive/`로 이동하거나 문서 최상단에 non-current 표시
- Test count 숫자 하나에 과도하게 의존하지 않고 critical suite/file manifest 검증
- Public package versions와 publish docs 자동 검증
- Example consumer tests는 package entry/dist를 사용하는 clean-install job에서 실행

### 로컬 검증 환경 주의

리뷰 시점 이 checkout의 `node_modules`는 sibling checkout의 `node_modules`를 가리키는
symlink였다. 이 때문에 example typecheck가 sibling의 stale package build를 참조했다.

탐색/확인:

```bash
readlink node_modules
npm ls @mir-stream/webchannel-saas @mir-stream/webchannel-client
```

Clean `npm ci` 환경에서 다음을 독립 검증한다.

- Root 및 workspace typecheck
- Package build 후 example consumer tests
- Plugin pack-and-load smoke
- Real NATS/live browser harness

### 완료 조건

- Current docs에 제거된 surface가 없음
- Version/test claims가 자동 검증되거나 변하기 쉬운 숫자를 제거
- Clean checkout CI가 example의 public package boundary를 검증
