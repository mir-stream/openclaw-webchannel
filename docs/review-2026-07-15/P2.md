## P2-1. Agent credential 및 identity-key rotation

### 실제 문제

Enrollment가 agent NATS JWT를 TTL 없이 발급하며 plugin identity key는 한 번 생성한 뒤 계속
사용한다. Runtime은 credential을 account startup 시 읽고 같은 JWT/seed로 계속 reconnect한다.
탈취된 credential은 수동 account revocation 또는 재-enrollment 전까지 유효할 수 있다.

### 현재 코드 지도

- Agent credential mint: `packages/saas/src/device-flow-enrollment.ts`
- User JWT claims/TTL: `packages/saas/src/nats-user-creds.ts`
- Plugin identity persistence: `packages/plugin/src/enrollment-client.ts`
- Credential load: `packages/plugin/src/consume-credentials.ts`
- Revocation primitive: `packages/saas/src/account-revocation.ts`
- Credential acquisition: `packages/plugin/src/acquire-credentials.ts`

### 코드 탐색 키

```bash
rg -n 'ttlSeconds|expiresAt|exp:|issue.*Credentials|mint.*creds' packages/saas/src
rg -n 'generated once|never rotated|identityKey|credentials\.json|consumeCredentials|Authorization Violation' packages/plugin/src
rg -n 'addRevocation|revocation' packages/saas/src
```

### 비교 참고

OpenClaw의 OAuth 계열 extension은 access token의 finite expiry와 refresh metadata를 명시적으로
보존한다. NATS credential은 OAuth refresh token과 같지 않으므로 구현을 복사하지 말고
“이미 enrollment된 agent identity에 묶인 제한된 renewal”을 설계한다.

찾아볼 sibling symbol:

```bash
rg -n 'expires_in|refresh_token|expiresAt' ../openclaw/extensions/chutes ../openclaw/extensions/google-meet
```

### 권장 계약

- `agentCredentialTtlSeconds`를 validated configuration으로 제공
- Enrollment result와 persisted credential에 credential ID/version, `expiresAt`
- Expiry 전 renewal 시 old/new overlap window
- Terminal NATS auth error를 refresh/re-enroll 상태로 분류
- Renewal request를 enrolled agent identity key로 인증
- Identity key 자체 rotation은 key ID와 overlap/revoke를 이용
- Resolver/account revocation propagation 책임과 SLA 문서화

### 사용자 경험

정상 rotation마다 사용자가 전체 pairing을 반복하게 하지 않는다. Identity 손상, explicit
revocation, 장기 offline 후 정책 만료 같은 경우에만 재-pairing을 요구한다.

### 필요한 테스트

- TTL claim과 `expiresAt` 일치
- Expiry 전 renewal, overlap 중 양 credential 동작
- Old credential revoke 후 reconnect 실패
- Renewal 요청의 agent identity signature 변조 실패
- Identity key rotation 중 browser pin migration
- Clock skew와 expired credential 오류 분류

### 완료 조건

- 무기한 agent credential이 기본값이 아님
- Credential과 identity key의 발급·갱신·폐기 상태가 관찰 가능
- 정상 rotation이 수동 pairing을 요구하지 않음

## P2-2. Account/agent-aware proactive outbound

### 실제 문제

Inbound와 approval 일부는 account-aware지만 generic proactive outbound는 lazy facade가 선택한
primary/first channel에 묶인다. Non-primary account의 cron/proactive content가 잘못 전달되거나
drop될 수 있다. 동일 peer가 여러 account에 존재하면 잘못된 deployment context로 내용이
노출될 수 있다.

### 현재 코드 지도

- Lazy transport facade와 primary binding: `packages/plugin/index-nats.ts`
- Outbound adapter: `packages/plugin/src/channel.ts`
- Approval account resolver: `packages/plugin/src/approvals.ts`
- Inbound context account stamp: `packages/plugin/src/inbound.ts`
- Session routing: `packages/plugin/src/session-route.ts`

### 코드 탐색 키

```bash
rg -n 'lazyTransport|boundChannel|primary|sendTextToAnyOpen|resolveApprovalTransport' packages/plugin
rg -n 'accountId|turnSourceAccountId|deliveryContext|lastAccountId' packages/plugin ../openclaw/src
```

### 참고 패턴

Telegram/iMessage는 operation마다 requested account를 해석하고 account identity를 outbound까지
전달한다.

```bash
rg -n 'resolve.*Account|accountId' ../openclaw/extensions/telegram/src/accounts.ts ../openclaw/extensions/imessage/src
```

### 권장 의미

- 모든 outbound operation은 명시적 `accountId`, multi-agent 이후 `agentId`를 요구
- Session-bound send는 persisted delivery context로 identity를 복원
- Truly untargeted broadcast는 별도 explicit fan-out API로 분리하거나 금지
- Identity가 모호하면 primary fallback 대신 failure
- Approval의 missing turn/source account도 모든 account에 claim하지 않게 함

### 필요한 테스트

- Shared peer가 account A/B에 있을 때 A proactive message는 A에서만 전달
- Account 없는 proactive send는 명시적 failure
- Restart 후 persisted delivery context가 같은 account/agent를 복원
- Missing/skipped runtime이 primary channel로 fallback하지 않음

### 완료 조건

- `boundChannel`/first-account routing 없음
- 모든 outbound receipt가 resolved account/agent를 기록
- Cross-account proactive isolation E2E 통과

## P2-3. Gateway/plugin single-active ownership

### 실제 문제

같은 account로 plugin process를 둘 이상 띄우면 각 process가 plain NATS subscription으로 같은
inbound를 받는다. Dedupe도 process-local이므로 동일 user message가 여러 agent turn/tool 실행을
만들 수 있다. Queue group만 추가하면 conversation key/history/approval ownership이 갈라질 수
있어 단독 해결책이 아니다.

### 현재 코드 지도

- NATS SUB command: `packages/plugin/src/nats-transport.ts`
- Account runtime/connection 생성: `packages/plugin/index-nats.ts`
- Ingress dedupe construction/state: `packages/plugin/src/ingress-dedupe.ts`, `index-nats.ts`
- Conversation key persistence: `packages/plugin/src/conversation-key-store.ts`

### 코드 탐색 키

```bash
rg -n 'SUB |queue|subscribe\(|IngressDedupe|dedupe|accountRuntimes' packages/plugin
rg -n 'conversation-keys|ConversationKeyStore|\.tmp|rename' packages/plugin/src
```

### 초기 정책

Account/agent identity당 single-active plugin을 공식 지원 정책으로 두고 distributed lease로
강제한다. Duplicate instance는 readiness 실패 또는 standby가 되어야 한다.

Active-active가 필요해질 때 함께 설계할 것:

- Queue/consumer ownership
- Shared durable idempotency
- Conversation key와 history store
- Approval first-write-wins
- Registration response ownership
- Agent identity key policy

### 10,000 key cap

한 설치 단위의 10,000 user cap은 제품 가정상 수용 가능하다. 하지만 cap 도달 시 oldest stable
conversation key를 삭제하면 연결된 device와 재등록 device가 서로 다른 key를 갖고 과거
history도 복호화하지 못한다. `ConversationKeyStore.getOrCreate`의 eviction을 admission failure로
바꾸고 operator에게 capacity error를 노출한다.

탐색:

```bash
rg -n 'MAX_KEYS|key cap|evicting oldest|getOrCreate' packages/plugin/src/conversation-key-store.ts
```

### 완료 조건

- Duplicate active plugin이 동일 turn을 처리하지 못함
- Capacity 도달 시 기존 key를 삭제하지 않고 새 admission이 명시적으로 실패
- Active-active를 지원한다고 문서화하기 전 shared ownership suite가 존재

## P2-4. RFC 8628 polling과 abuse control

### 실제 문제

Library가 poll interval을 응답에 담지만 실제로 last poll을 기록하거나 조기 poll에
`slow_down`을 반환하지 않는다. Invalid interval/expiration 값도 충분히 검증하지 않는다.
Issuer HA에서는 HTTP process별 limiter만으로 device-level protocol semantics를 보장할 수 없다.

잠재 계약 불일치: plugin poll client(`packages/plugin/src/enrollment-client.ts`의 `httpPost`
주석)는 `slow_down`을 기대 응답 코드로 이미 나열하지만 server는 이를 절대 내보내지 않는다.
`slow_down` 구현 시 client 쪽 처리가 실제로 동작하는지 함께 검증한다.

### 현재 코드 지도

- Enrollment constructor/options, `poll`: `packages/saas/src/device-flow-enrollment.ts`
- Error/result types: `packages/saas/src/device-flow-types.ts`
- Reference HTTP poll route: `packages/saas/reference/enrollment-server.ts`

### 코드 탐색 키

```bash
rg -n 'pollIntervalSeconds|interval|slow_down|authorization_pending|poll\(' packages/saas
```

### 책임 분리

Library/store:

- Device code별 last poll과 slowdown state atomic 기록
- RFC 상태 전이와 `slow_down`
- Finite positive expiry, minimum interval validation

Integrator/edge:

- IP, account, global rate limit
- Bot/abuse detection
- Reverse proxy connection/body/time limits

### 필요한 테스트

- Minimum interval 이전 반복 poll
- `slow_down` 후 interval 증가
- 두 issuer instance의 concurrent poll
- Zero/negative/NaN/Infinity config 거부
- Expired/approved/denied terminal response 일관성

### 완료 조건

- Device-level poll semantics가 process-local state에 의존하지 않음
- Reference server가 library semantics와 edge rate limit을 모두 사용
